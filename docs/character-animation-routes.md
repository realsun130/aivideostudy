# 角色动画：可以尝试的方向（灵感清单 ⚠️ 待测试）

> **这不是流程，也不是规范。** 下面每条都只是一个可能的方向，来自别人公开的做法。做片时可以挑一条试，可以混着用，也可以一条都不用。条目之间没有先后顺序，也没有哪一步是必须的。
> 所有内容标 ⚠️ 待测试。在至少一次 Track S 跑通前，本文件冻结，只做纠错。
> 我们现有的硬规矩不因本文改变：ML §1/§12（每帧是帧号的纯函数）、ML §10（拉伸与步态数字约束）、Bot D 纯程序化成本优先（[bot-d-contract-programmatic.md](../bot-d-contract-programmatic.md)，已锁定）。下面凡是和这些冲突的地方，都只**标出来**，不改决定。

## (a) 先做好角色模型，再导演表演

- **来源**：[@akokoi1 fight](https://x.com/akokoi1/status/2103149275945517546)（60 秒 3D 打斗，约 2,000 行代码）。[作者补充](https://x.com/akokoi1/status/2103149539880562718)分三步：先用 Three.js 做角色，调到满意；再基于这个模型要 60 秒电影感打斗；最后加声音导出。整理自 AO55B（见 [STYLE_REFERENCE_CASES_AO55B.md](STYLE_REFERENCE_CASES_AO55B.md)），作者自述，九帧抽样，未核实。
- **它解决什么**：把「角色长什么样」和「角色怎么动」拆成两次确认。角色先被人看过、认可，后面的表演只能在这个模型上做，不容易走样。思路和我们「先审静帧再做动效」一致。
- **成本／许可**：Three.js MIT；只用浏览器，不花视频模型的钱。角色造型须是我们自己的。
- **4060 8GB**：浏览器 WebGL 足够；可用 ML §9 的子采样出终版。
- **和现有规则**：3D 方向本来就有备忘（[3D_DIRECTION.md](3D_DIRECTION.md)，⚠️ 备忘未实施）。这条可以作为那份备忘的一个具体做法。
- **可以先试**：用 Three.js 搭一个低模查理王（只要头、耳、躯干、前肢），出一张角色转面联系表给你看，认可后再试一个 3 秒的「抬头笑」动作。

## (b) Blender 粗模定机位和走位，再交视频模型出最终画面

- **来源**：[@OriSilver Blender 草模到 Seedance](https://x.com/OriSilver/status/2102817977812824335)（AO55B atlas「广告／发布片 × 写实」）。作者说：先给一段镜头风格参考片，Claude 通过 MCP 抽样，在 Blender 里重建机位、走位和分镜，导出约 30 秒草模；再把草模和自己的角色一起给 Seedance 2.5 当参考，出最终画面。作者自述，调用日志与源片未核。
- **它解决什么**：视频模型最难控制的是镜头和空间关系。先用粗模把「镜头怎么走、角色站哪、动到哪」定死，模型只负责把粗模画好看。
- **成本／许可**：Blender 免费（GPL，渲染产出归我们）。最终画面要用视频模型：云端按秒收费，商用要看具体服务条款。
- **⚠️ 冲突**：最后一步需要视频模型，和 Bot D「纯程序化、不上图生视频、成本优先」的锁定决定冲突。这里只标出，不改决定。
- **4060 8GB**：Blender 粗模（Workbench／EEVEE）没问题。若想不花云端费用，本地 8GB 只能考虑小号开源视频模型（例如 1.3B 参数级别），画质、时长、是否支持参考图都要实测，**未在你的机器上测过**。
- **可以先试**（不碰视频模型的一半）：只做前半段，用 Blender 粗模给某一镜定机位和走位，导出灰盒动态分镜，作为我们 Shot List 的参考。这一半和现有流程不冲突。

## (c) 先生成、再描摹（generate then trace）

- **来源**：@0xkerazcity 的 X 长文《Opus 5.5 Motion Playbook》（[原帖](https://x.com/0xkerazcity/status/2111079749342675440)）中的混合路线：用视频模型生成一段底层动作，再用代码在上面逐帧重画，让画风统一。本条按之前对这篇长文的拆解整理，具体参数以原文为准。
- **它解决什么**：手写代码很难让角色动得自然（重心、惯性、细小的身体反应），视频模型动作自然但画风会漂。用模型的动作当「参考底片」，代码只负责描出统一的画风，各取所长。
- **和 (b) 的关系**：(b) 是「代码定结构 → 模型出画」，(c) 反过来，是「模型出动作 → 代码出画」。
- **成本／许可**：同 (b)，要用视频模型；底片也要能商用。
- **⚠️ 冲突**：同 (b)，和 Bot D 纯程序化决定冲突，只标出。
- **4060 8GB**：描摹那一半（姿态估计、关键点提取、代码重画）本地能跑；生成那一半同 (b)。
- **可以先试**（不碰视频模型的版本）：底片换成**可商用的真实素材**，比如自己拍的狗、CC0 视频，或 [3D_DIRECTION.md](3D_DIRECTION.md) 里已核实许可的动作库。提取关键点，套到查理王骨架链上，用代码重画一个 2 秒动作，看看描摹这一步能不能保持我们的画风。

## (d) Papermotion：纸片骨骼 + 物理

- **来源**：[francozanardi/papermotion](https://github.com/francozanardi/papermotion)，MIT。README 自述引擎、工具、示例全部由 AI 写成，「没人逐行读过代码」。
- **本机实测**：在盒子上跑通。需要 Node 22.18 及以上（盒子自带的 Node 20 不行，另装了 22.20），系统 Chrome 加 ffmpeg。`rooftops`（猫走屋脊、跳屋顶、惊飞鸽子）10 秒 960×540 草稿版，8 个页面并行，3.3 秒渲完 300 帧，CPU 即可。
- **骨骼怎么搭**（`src/rig/Skeleton.ts`、`Bone.ts`）：
  - 每根骨头写成 `{name, parent, length, angle, at, spring, limits}`。子骨头从父骨头末端出发（`at` 可指定在父骨头上的位置 0–1），所以**关节由构造保证不会断开**。作者踩过的坑：头用位置弹簧挂在身上，跑起来头会掉。
  - **骨长永远不变**，动的只有角度。我实测走路 8 秒，所有骨头长度误差为 0.00%，所以骨头本身不会被拉长。
  - 「活」靠角度弹簧：`stiffness`、`damping`、`inertia`（父骨转动时保留世界朝向的比例，产生拖拽和滞后）、`sway`（骨根加速度引起摆动，产生跟随）。`limits` 限制关节角度，可以防膝盖反折。
  - 阻尼比换算：ζ = damping ÷ (2√stiffness)，质量取 1。示例的小孩头 170/13 → ζ≈0.50，脊柱 260/22 → ζ≈0.68，猫头 160/12 → ζ≈0.47，都比 ML §3 的「高级」档 0.7–0.85 更活泼。
  - 两骨 IK `reach(upper, lower, target, bend)` 可以让手去够目标；`boneFrame()` 和 `uprightFrame()` 让道具、头、脸跟着某根骨头走。
- **走路怎么做**（`src/rig/Gait.ts`）：步相随**走过的距离**推进，每 `step` 像素走半个周期；每只脚的目标点 = 髋部 x + sin(相位) × `footReach` × 奔跑程度，用 IK 放到地面上；抬脚高度 = max(0, cos(相位)) × `footLift`；还有髋部起伏、前倾、手臂反向摆动、跛脚参数。四足用相位 [0, ½, ¼, ¾]。
- **防滑步，我实测的结果**：作者笔记的规则是 `footReach ≈ step / 2`。我用示例小孩的参数（step 105，footReach 56，runSpeed 600）跑了数值测试，统计每次着地期间脚在世界坐标里滑了多远：
  - 全速跑（600 px/s）：每次着地滑约 12 px，基本不滑。
  - 慢走（150 px/s）：每次着地滑约 73 px，身体每步才走 105 px，**明显滑步**。把 footReach 改成正好 step/2 也一样（约 75 px）。
  - 原因有两个：脚的摆幅乘了「奔跑程度」（速度 ÷ runSpeed），慢走时脚几乎不往后蹬；而且脚是按正弦摆的，着地那一刻脚的速度并不是 0。所以这条规则只在接近全速时成立，**达不到你「不许滑步」的要求**。
  - 如果借这个引擎，可以考虑改成：脚着地时把世界坐标锁住，IK 腿去够这个固定点；抬脚时沿弧线移到下一个落点。验收标准是：着地期间脚的世界 x 变化 ≤ 1 px（对应 ML §10「落脚瞬间速度 0」）。
- **挤压拉伸**：猫跳跃用 `Leap` 先算好从 A 到 B 的抛物线（起跳拉长、空中收身、落地前伸），落地时给挤压弹簧一个冲量。小孩被作者称为「rubber-hose（橡皮管）」角色：四肢用 `paper.tube` 穿过关节点画出来。远侧那只手是一个被弹簧拉向目标的物理点，从代码看，手离得远时前臂画出来可能被拉长。这是读代码得出的风险，我没有逐帧量。
- **物理**：确定性 Verlet 世界（风、地面、单向平台、软硬碰撞体）、绳、软体、`Strand`（会记住形状的链，用于尾巴、触角、头发）。
- **节奏**：`Beats`。每个节拍「持续做某事，直到满足条件才结束（超时兜底）」，不是按秒表排；并把一个动作拆成「对位」和「执行」两个节拍。声音来自同一批事件，比如脚落地的地方就响脚步声。
- **渲染**：Canvas 2D 的纸片渲染器。撕边会抖动，有纤维纹理、投影、轮廓光。**一个角色是一张纸**：各部件合成一个剪影，只有一个影子、一个纹理，花纹裁剪在剪影里面。
- **⚠️ 和我们纯函数规则的冲突**：它是固定步长、只能往前跑的模拟。官方说法是 `Stage.renderFrame` 不能倒退，并行渲染时每个页面要先「模拟走过」前面的帧。这不满足 ML §12「任意帧可单独求值」。可以借用的方式和 ML §8 一样：先完整模拟一遍，把每帧的骨骼角度存成 JSON（烘焙），渲染时按帧号查表。
- **对应查理王骨架链约定**（只是对照，不改 rig 约定）：
  - 鼻尖 → 两嘴角 → 下巴：头骨下挂吻部骨，两嘴角用 `at` 挂在吻部骨上，下巴单独一根骨，用 `limits` 限制张嘴角度。
  - 耳根 → 耳中 → 耳下缘：三节骨链，每节带 `inertia`/`sway` 弹簧，耳朵会自然甩、滞后（对应 ML §4「耳朵比身体更松」），或者直接用 `Strand`。
  - 胸口 → 肩 → 肘 → 腕 → 手机：胸口为根，肩用 `at` 挂上，肩、肘两骨用 `reach()` 让腕去够手机；手机画在腕骨的 `boneFrame` 里，自然贴手。
- **可以先试**：把 `Skeleton` 和 `Bone` 这两个文件（约 180 行，MIT，保留版权声明）移植过来，搭查理王的耳链。烘焙 3 秒「大笑抖动 + 耳朵甩动」，逐帧检查骨长误差（应为 0）和耳尖轨迹是不是弧线。

## (e) p5.brush 手绘角色（ClaudeAnimationBase）

- **来源**：[JohnHeibel/ClaudeAnimationBase](https://github.com/JohnHeibel/ClaudeAnimationBase)，MIT。依赖 p5.js（LGPL-2.1，作为库原样引用即可，改了 p5 本身再分发才有额外义务）和 [p5.brush](https://github.com/acamposuribe/p5.brush)（MIT）。AO55B 还收录了一条[复用这个仓库做的个人故事](https://x.com/servasyy/status/2104039075175182487)。
- **本机实测**：在盒子上跑通。没有显卡，要加 `--soft-gl` 用软件渲染。只有天空的帧约 0.15 秒一帧，带水彩填充的帧 21–23 秒一帧。联系表正常出图。多进程渲染时页面加载超时，所以短片段改用单进程渲染。作者说有显卡时快得多，你的 4060 上没测过。
- **角色怎么搭**：**不是骨骼**。Clawd 是一个参数化的绘制函数 `clawd(x, y, u, 选项)`：方块身体 10u×6u，四条小方腿，两个手臂小突起（`aL`/`aR` 角度），外加眼睛、嘴、帽子和情绪符号。转身不做 3D 旋转，而是画五个关键视图（正、3/4、侧、背 3/4、背），转身时在 0.12–0.25 秒内逐个切换，并加拖影。
- **走路**：腿的相位 = 走过的距离 ÷ 4u；侧视时对角两条腿一起摆，摆幅 ±0.55u，往前摆时抬起。我按公式算了一下：着地那条腿每步只往后扫 1.1u，身体却走了 2u，所以脚每步往前滑约 0.9u（约为步长的 45%）。对小方块卡通角色无所谓，**不满足你的防滑步要求**。
- **挤压拉伸**：`scale(1 + 0.6·sq, 1 − sq)`。跳跃落地 sq=0.22 时面积约 −11.7%；惊讶「take」强度为 1 时竖向拉长 26%，面积 +6.4%。面积在 ±10–12% 附近，但**竖向拉长超出 ML §10 边长 ±12% 的上限**。作者的动画原则里写的是「保体积」，实际只是近似保。
- **时间与节奏**（最值得借）：
  - 每一镜写成 `fn(t, lt, dur)`，**严格是时间的纯函数**，不带状态、不做逐帧物理，和我们 ML §12 完全一致。
  - 线条每秒「抖」12 次（boil），每个元素单独设种子 `boilSeed(key)`，这样会动的东西不会让后面不动的东西跟着乱抖。
  - **「reads」时间表**：每镜按顺序列出观众要看懂的每件事，每件给开始和结束时间，任意两件重要的事不能重叠。作者例子：初版把结尾 7 件事挤在 1.3 秒里，没人看得懂；改成约 4 秒才看清。
  - `emotions()` 换表情时依次做：先眯眼并挤压（预备）→ 在眯眼时换脸 → 按新情绪大小来一个 take → 带回弹进入新情绪的待机动作。表情从不「一帧硬切」。
  - 所有待机动作都锁在同一个 BPM 上。
- **检查工具**：`render.mjs` 可以出联系表、每帧条带、全分辨率局部，还有 `--crop-at`：**跟着一个世界坐标点（比如一只脚）逐帧裁图**，专门查脚有没有贴地、道具有没有贴手。
- **对查理王**：它没有骨骼链，借不了 rig。能借的是表演层（表情换场的预备、take、回弹）、reads 时间表，以及跟着脚裁图的检查方式。
- **可以先试**：拿一个已审过的镜头写一张 reads 时间表，看看现在哪些事挤在一起；再给 `tools/` 写一个「跟着世界坐标点裁图」的小脚本，用来查脚和手机。

## (f) 一个角色穿越年代（Doodle history）

- **来源**：[用涂鸦讲述人类史](https://x.com/oalanicolas/status/2107958931230241037)（作者报告用的是 Fable 5.5，不是 Opus）。88 秒、16 个时代，**画技和音乐随时代变**；九帧取样可见**同一个手绘角色贯穿各个年代的画框**，从纸墨一路变到像素游戏风格。同类还有[四万年艺术史与猫的支线](https://x.com/cherry_mx_reds/status/2106095190285144331)：画家和猫穿过洞穴、埃及、马赛克、文艺复兴、现代。都是作者自述，九帧取样，未核实。
- **它解决什么**：历史讲解片容易像「地图 + 字卡」的幻灯片。有一个固定角色，观众就有人可跟，每次换时代都有一个记忆点。画风跟着时代换，正好把「转场」变成内容本身（呼应 ML §13 媒介原生转场）。
- **成本／许可**：纯程序化就能做，不冲突。角色必须是我们原创的，不能用他人 IP（钢铁侠、蜘蛛侠、真人肖像那类案例只看结构）。
- **4060 8GB**：无特殊要求。
- **和我们的历史线**：万圣节历史片现在没有贯穿角色。下一部历史片想加，可以考虑用一个很简单的角色（比如一盏会走的小灯），每个时代换一种画法，但比例锁定行不变（ML §4）。
- **可以先试**：用万圣节已审的两个时代（萨温节篝火、美洲南瓜灯）各画一张同一个小角色的静帧，只换画法、不换比例，先看静帧成不成立，再决定要不要做动态。
